# Moonstone 0.8.0

Native Lua modules on Linux and the BSDs no longer carry a copy of the Lua
runtime. Builtin, command, and CMake rocks used to link the runtime's static
`liblua.a` (or `libluajit-5.1.a`) into every module; they now leave the Lua C
API undefined and take it from the process that loads them, as LuaRocks does.
macOS (`-undefined dynamic_lookup`) and Windows (import library) are unchanged.

- Rocks that ship compatibility definitions of runtime functions now build.
  `luasystem`, and with it `busted`, previously failed with
  `duplicate symbol: luaL_setfuncs` on LuaJIT.
- Modules built for a runtime's ABI load in any host with that ABI, using the
  host's VM. For example, `luajit@2.1` modules load inside Neovim.
- Custom ELF runtime packages must export the Lua C API (`-Wl,-E` or a shared
  `liblua`). Moonstone's own runtimes already do. See
  [Platforms](../PLATFORMS.md#native-lua-modules-and-the-lua-c-api).

## Upgrade

Native artifacts are rebuilt with different bytes. A `moonstone.lock` written
by 0.7.x or earlier that pins native modules still replays from a store that
holds those artifacts, but keeps using the old modules. On a clean store it
stops with `ArtifactHashMismatch`. Either way, re-lock once:

```bash
moon sync --update
```

Versions stay within your constraints; commit the updated lockfile.
