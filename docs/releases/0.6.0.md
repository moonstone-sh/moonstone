# Moonstone 0.6.0

Released 2026-10-15 (tag `v0.6.0`). One package can now serve several Luas:
Moonstone knows which Lua an environment runs, picks the right file for it,
and tells the code and the build tools what it picked.

The full contract is in
[`PROJECT_ENVIRONMENT.md` → Flavors](../PROJECT_ENVIRONMENT.md#flavors-one-package-for-several-luas).
This page is what changed and what to do about it.

## What's new

### Flavors

A *flavor* is what Lua source can observe about where it runs: the language
(`lua51` … `lua55`, `luajit`, `luau`) and the host os and arch. Its id reads
`lua54-aarch64-macos`, `luajit-x86_64-linux`. It is deliberately not the C
ABI, which only native modules see.

`moon sync` records the environment's flavor in `.moonstone/env/env.toml`
under `[target]`, and `moon exec` / `moon run` export it as
`MOONSTONE_TARGET`. A value the caller already set wins, which is how a build
tool is asked to specialize for a flavor other than the host's.

### Variant files

A package can ship one file per flavor for the same module:

```text
src/lexlib/lexer.lua           fallback
src/lexlib/lexer@lua54.lua
src/lexlib/lexer@luajit.lua
```

`moon sync` projects exactly one of them as `lexlib/lexer.lua`, so consumers
keep writing `require("lexlib.lexer")`. Selection happens at link time and
costs nothing at runtime. The rules, in short:

- Tags go in the order language, os, arch, at most one each.
- `@lua51` also matches LuaJIT, less specifically than `@luajit`. Luau never
  inherits `@lua51`.
- The winner must be at least as specific as every other match on every
  dimension; two files that are each more specific in a different way stop
  the sync instead of one being picked silently.
- A name whose tags are not all in the vocabulary is an ordinary module, and
  `_` is never a separator, so existing names like `parser_luajit.lua` keep
  their meaning.

### Generated `moonstone` modules

Every environment now contains:

| module | contents |
|---|---|
| `moonstone.target` | constant table: `id`, `family`, `level` (51 … 55), `os`, `arch`, `runtime = { name, version, abi }` |
| `moonstone.project` | constant table: `name`, `version`, `kind`, `description`, `dependencies` (sorted) |
| `moonstone.variants` | the selection rule in Lua (`parse`, `match`, `select`, `suffixes`, `resolve`) and `install()`, a searcher for a project's own variant files |
| `moonstone` | `{ target, project, variants }` |

Both data modules carry LuaLS annotations and nothing machine-specific, so
the same project and flavor always produce the same bytes. A project's own
`src/` is not projected; call `require("moonstone.variants").install()` once
in the entry point to resolve its variants at runtime.

### `@` in artifact paths

`moon artifact create` accepts `@` in archive paths, so packages can publish
variant files. Earlier versions fail with `InvalidVirtualPath`.

## Behavior changes

These can turn a sync that passed under 0.5.x into an error:

- **The `moonstone` module name is reserved.** A dependency that projects a
  `moonstone` or `moonstone.lua` module fails the sync with `ModuleConflict`.
  None of the packages in the Moonstone workspace or the local store do.
- **Malformed variants are errors.** `lexer@linux@lua54.lua` (out of order) or
  `lexer@lua53@lua54.lua` (repeated dimension) fails with
  `InvalidModuleVariant`; two equally specific matches fail with
  `AmbiguousModuleVariant`. Both name the file and the fix.
- **Variant files are no longer projected under their tagged names.** Before
  0.6.0, `foo@lua54.lua` landed in the environment as a module literally named
  `foo@lua54`. Now it is either projected as `foo.lua` or left out.

## Upgrading as a package author

Consumers may still run an older `moon`, or no Moonstone at all (embedded Lua,
browser engines). To stay safe for them:

- **Always keep an untagged fallback** that works on every Lua you support.
  An older `moon` ignores the tags, projects every file verbatim, and the
  fallback is what `require` finds.
- **Never hard-require `moonstone.*` from library code.** Guard it with
  `pcall` and fall back to runtime detection.
- **Publishing variant files needs 0.6.0 in your release pipeline.** If other
  projects bundle your modules into their own artifacts (for example a tool
  built with Ballad's `layout.exec`) with an older Moonstone, their packaging
  fails on the `@` file. Ballad 0.4.6 and Hydronium v0.4.0 keep their variants
  out of their packages for that reason, and ship only the fallbacks.

## Known limits

- No header pragma (`--moon:build <expr>`) for conditions tags cannot express.
- No multi-flavor test matrix (`moon test --flavors …`).
- `moonstone.lock` does not record the flavor.
- Luau is in the vocabulary, but Moonstone does not provision a Luau runtime.

## For build tools

A bundler that specializes per flavor (Quaver) reads `MOONSTONE_TARGET`, picks
files with `moonstone.variants` rather than reimplementing the rule, and may
fold `moonstone.target` / `moonstone.project` fields as constants when they
are bound with `local x = require(...)` and never reassigned. The details,
including what must not be folded for a non-host target, are in
[`PROJECT_ENVIRONMENT.md` → Contract for build tools](../PROJECT_ENVIRONMENT.md#contract-for-build-tools-quaver).
